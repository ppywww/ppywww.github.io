## 一、需求池机制（三条规则）

1. **任何新需求先入池，不直接开发。** 入池即登记，标注来源与优先级建议。
2. **仅在当前里程碑（MVP / M6 上线）完成后**，由老板从池中挑选，批量进入下一迭代。
3. **已锁定项（见 `docs/00-decision-log.md` §一）不可从池中绕过**——要改必须先由老板明确同意并改决策日志。

### 优先级定义

| 级别 | 含义 | 处理时机 |
|---|---|---|
| **P0** | 阻塞上线，缺了第一版不能用 | 当前迭代 |
| **P1** | 重要但不阻塞，缺失体验明显下降 | MVP 后第一个迭代 |
| **P2** | 锦上添花，有更好 | 排期机动 |
| **P3** | 想法，未验证价值 | 仅记录，不排期 |

## 四、已识别但**建议不做**

| 需求 | 不做的理由 |
|---|---|
| 用户注册 / 后台 CMS | 静态站定位，作者即唯一编辑，收益远低于成本 |
| 服务端渲染 SSR | 无动态数据，纯增加运维面 |
| 多语言 i18n | 老板已定中文为主（P-02） |
| 付费内容 / 会员 | 与产品定位不符 |
| 评论区自建后端 | Giscus 已满足，自建需运维 |
| 图片 CDN / 相册系统 | V2 再议 |
